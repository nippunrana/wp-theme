# Cloudflare Turnstile

Code: `inc/turnstile.php` (widget, check, form hooks, cache clearing), the getter `egnitech_one_get_turnstile_settings()` in `inc/helpers.php`, and the **Integrations** tab in `inc/admin-options.php`.

- **Turnstile is the theme's only bot check** (owner's decision, 20 Nov 2026). Google reCAPTCHA was removed with its settings and its helper `egnitech_one_get_recaptcha_settings()`. **Never** add reCAPTCHA or a second challenge back. A site that saved reCAPTCHA keys still holds three `egnitech_one_recaptcha_*` rows, the secret among them; nothing reads them.
- **Turnstile starts only when the switch is on and both keys are saved.** Until then no widget is printed and nothing is checked. **Never** loosen this to the switch alone: the switch saved without a secret would refuse every login. A saved secret the site can no longer decrypt counts as missing (`stored-secrets.md`), so changed salts switch Turnstile off instead of refusing every login.
- **It fails closed, including when Cloudflare cannot be reached.** A missing, wrong, reused or expired token refuses the form, and so does a check that errors or times out. If that locks the administrators out, run `wp option update egnitech_one_turnstile_enabled no` on the server (or blank that row in the options table). Then clear the page cache from the admin bar, because WP-CLI cannot (`page-cache.md`).
- **Each check is limited to a request from its own form. Never widen one to the bare hook.** `authenticate` also runs for XML-RPC logins and on every visit to wp-login.php. `lostpassword_post` also runs when an administrator sends a reset link from the Users screen. None of those carry a token, so a check on the bare hook blocks them.
- **Cloudflare accepts a token once, and WordPress validates every comment twice in one request.** `egnitech_one_turnstile_verify()` keeps Cloudflare's answer per token for the request. **Never** remove that, or every genuine comment is refused as "already spent".
- **The comment check runs on `pre_comment_approved`, after WordPress's own checks.** **Never** move it to an earlier hook such as `pre_comment_on_post` or `preprocess_comment`: a comment refused for a missing email would use up the token, and the visitor's corrected retry would fail.
- **Every form that posts to wp-login.php must print the widget**, or every login from it fails. That is why `login_form_middle` is hooked: `wp_login_form()` and the Login/out block's form post there too. A custom login form needs `egnitech_one_turnstile_widget( 'login' )` inside it.
- **Not covered:** WooCommerce checkout (and account creation there), XML-RPC, the REST API, and contact-form plugins. Checkout validation belongs in a plugin. Most form plugins have their own Turnstile setting that takes the same keys.
- **`api.js` loads from Cloudflare's own address with no version.** This is the one exception to the versioning rule in `assets-and-versioning.md`: Cloudflare says a cached, proxied or self-hosted copy breaks when they update it. **Never** pass it through `egnitech_one_asset_version()` or copy it into the theme.
- **The secret key is used only by `egnitech_one_turnstile_verify()`**, which decrypts it with `egnitech_one_read_secret()` (`stored-secrets.md`). The getter checks that it can be read but leaves it out of what it returns, on purpose. **Never** add it to the getter, a script or a REST response.
- **Changing the switch or either key clears the whole page cache.** **Never** remove that. Without it, cached posts keep a comment form with no widget while the server starts demanding a token, so every comment on them is refused.
- **The hostname Cloudflare returns is not checked**, though Cloudflare's docs suggest it: the test keys report `example.com`, so the check would fail every test.
- **The `action` is compared only when Cloudflare returns one.** Real widgets always do; the test keys never do.
- **Test only with Cloudflare's test keys** (Turnstile docs, Troubleshooting > Testing). Their secrets accept the token `XXXX.DUMMY.TOKEN.XXXX`, so a form can be posted with `curl`: secret `1x0000000000000000000000000000000AA` passes, `2x…AA` fails and `3x…AA` reports a spent token. Pair them with site key `1x00000000000000000000AA` in a browser. **The passing key accepts a token any number of times, so it cannot show a token checked twice.** For that, answer siteverify through a `pre_http_request` filter that says yes once per token.
